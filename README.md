Geyouyou Zhu & Namgyal Kunsang

When we first started working on our project after Stage 2, we chose to separate the work into two different .qmd files to avoid interfering with each other’s work. While we knew how to resolve any GitHub merge conflicts through our certification, we decided it would be more convenient to have our own files to avoid any instances where all of our data might have been removed due to forgetting to pull or commit to our repository. Initially when we began our data wrangling, we regularly made commits through our own .qmd file and pushed them to GitHub. Then the other person could pull the updates and copy the relevant code into their own .qmd file. 
It was most utilized when we first started, since drilling into specific parts of the list was difficult and required trial and error. But later on, we stuck to our own .qmds and didn’t need to commit as often, since we focused on different parts of the question that didn’t require each other’s data. This work flow significantly improved our efficiency by allowing us to work independently without interfering with each other’s progress, while still making it easy to share and integrate our results. 
We also scheduled several one-hour meetings throughout the week to discuss the project content and coordinate our work, and had one of us go during office hours to get some clarification about a problem in the code. We divided the main question down into two smaller and more specific questions, with each of us taking responsibility for one. Even though we worked on these questions separately, we stayed in communication whenever challenges arose, discussing problems together and finding solutions as a team.
Although splitting the work into two .qmd files helps us avoid many potential merge conflicts, we both recognized that working in a single file could be a valuable experience for professional fields. In future projects, we would like to try collaborating within one shared file to become more familiar with resolving merge conflicts and improve our teamwork by using GitHub.
Once we had each completed our own parts, we managed to integrate all the code into the main test file that we created when we did Stage 2. The collaborator pushed her own file and the owner pulled it down, and then copied all files into the main file and pushed it to GitHub. Overall, this was a very effective way to avoid the issue of having merge conflicts.
